VSCode 中 Kilo 扩展的代理机制解析与分流配置（http.proxy 与 noProxy）

本文最后更新于 2026年11月18日 晚上

在日常研发中，经常会遇到这样一种网络分流需求：AI 编程插件需要走代理访问外部模型 API，但同时又要直连公司内网的私有模型网关或本地调试服务（如 localhost、*.rustfisher.com）。

问题背景

VSCode 本身并没有提供“按单个扩展独立设置代理”的开关。如果全局开启代理，内网域名或本地接口可能会被误转发导致连接超时；如果彻底关闭代理，外部模型又无法连通。

  • VSCode Version: 1.146.0 (user setup)
  • Kilo 7.8.27

底层机制：Kilo 如何透传代理环境变量

虽然 VSCode 没有细粒度的扩展代理开关，但 Kilo 扩展内部自己实现了一套代理环境变量构建逻辑，恰好提供了可用的调节点。

查看其核心实现逻辑（buildProxyEnv）：

从源码可以看出，Kilo 在启动底层工作进程时，会读取 VSCode 的三个核心网络配置项，并将其翻译为标准的系统环境变量透传给它拉起的 kilo.exe 子进程：

  1. http.proxySupport：当设置为 "off" 时，会主动清空 HTTP_PROXY、HTTPS_PROXY 和 NO_PROXY，强制子进程直连。
  2. http.proxy：映射为子进程的 HTTP_PROXY 与 HTTPS_PROXY。
  3. http.noProxy：将配置的数组拼接为逗号分隔的字符串，映射为子进程的 NO_PROXY。
